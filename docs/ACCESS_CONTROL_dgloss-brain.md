# ディグロス・ブレイン 権限設計書（v0.1 ドラフト）

「全社で使う。ただし、どの情報に誰がアクセスできるかは制御する」という決定（2026-07-14 石井）を受けた設計。

---

## 1. 基本原則

1. **頭脳は権限を"作らない"、元システムの権限を"通す"** — アクセス可否はNotion／Google Workspace側の権限が源泉。頭脳側に独自の権限DBを持たない（二重管理は必ずズレる）
2. **質問者を必ず識別する** — 匿名の質問は受け付けない。Google Chatボットは質問者のGoogleアカウントを常に取得できる
3. **迷ったら見せない** — 権限が判定できない情報は回答に使わず、「この情報には権限が必要です。○○（オーナー）に確認してください」と案内する

## 2. 情報分類レベル

全社の情報を5レベルに分類する。**このマトリクスが権限設計の中心**であり、Notion・Driveのフォルダ／チームスペース構成をこの分類に揃えることが導入作業の本体になる。

| レベル | 分類 | 具体例 | アクセスできる人 |
|---|---|---|---|
| **L1** | 全社公開 | ビジョン、ポリシー、業務マニュアル、経費精算ルール、組織図、用語集 | 全社員 |
| **L2** | 部門限定 | 事業部ページ、顧客DB・案件情報、営業資料、部門KPI | 所属部門メンバー＋経営陣 |
| **L3** | 経営・管理職 | 事業計画、財務数値、経営会議議事録、M&A・提携検討 | 役員＋指定管理職 |
| **L4** | 機微情報 | 人事評価、給与、懲戒、健康情報、個人情報 | 人事担当＋役員のみ |
| **P** | 個人スコープ | 本人のGmail、カレンダー、個人メモ | 本人のみ |

運用ルール：
- 全ページ・全フォルダはいずれかのレベルに属する。**未分類はL3扱い**（迷ったら見せない）
- レベルはNotionのチームスペース／Driveの共有ドライブ単位で付与する（ページ単位の例外は最小限に）
- 分類の変更はオーナー＋管理者の承認制

## 3. フェーズ別の実現方式

### Phase 1（Claudeアプリ＋コネクタ）— 自動的に守られる
各自が自分のアカウントでNotion・Googleコネクタを認証するため、**本人に見える情報しか検索されない**。頭脳側の追加実装は不要。
ただし前提として「Notion/Drive側の権限が §2 のマトリクス通りに設定されていること」が必要 →「権限棚卸し」（§5）を先に実施する。

### Phase 2（Google Chatボット）— ここが設計の本丸

ボットは共有アカウントで動くため、素朴に作ると「ボットに見える情報＝全員に見える情報」になってしまう。対策を情報源ごとに分ける：

| 情報源 | 方式 |
|---|---|
| Notion | **ホワイトリスト方式**：ボット用Notionインテグレーションには L1・L2 のチームスペースのみ共有する。L2はボットが質問者の所属部門を確認してからフィルタ（組織図データを参照）。L3・L4はボット経由では原則回答しない（「Claudeアプリで直接確認してください」と案内） |
| Google Drive | ボットのサービスアカウントに **ドメインワイド委任はしない**。質問者ごとのOAuthトークンで質問者本人としてDrive APIを叩く（初回のみ各ユーザーが連携許可） |
| Gmail（個人スコープ） | 同上。**本人のOAuthトークンでのみアクセス**。他人のメールは技術的に読めない構成にする |
| 経営陣向けL3回答 | Phase 2では対応しない（Claudeアプリ側で完結）。需要が強ければ「役員専用Chatスペース＋役員権限トークン」を別途構築 |

### Phase 3（RAGインデックス）— ACL同期
インデックスを作る場合、各チャンクにメタデータとして `level`（L1〜L4/P）と `allowed_groups`（部門・ロール）を付与し、検索時に質問者の属性でフィルタする。メール由来のチャンクはユーザーごとの名前空間に分離する。ソース側で権限が変わったら同期ジョブがメタデータを更新する（最大遅延24時間を許容）。

## 4. 全メール取り込みとプライバシー

「全メールをインプットしたい」（決定済み）に対する推奨構成。**メールは機微性が高く、"全員が全員のメールを検索できる"構成は避けるべき**。目的別に分けて実現する：

| 目的 | 方式 | 見える範囲 |
|---|---|---|
| 自分の過去のやり取りを探したい | 本人OAuthで本人のGmailを検索 | 本人のみ |
| 顧客とのやり取りを組織で把握したい | **顧客ドメイン宛/発のメールのみ**抽出し、顧客DBの該当顧客ページに要約を自動転記（夜間バッチ） | その顧客を扱う部門（L2） |
| 共有窓口（info@等）の対応履歴 | 共有メールボックスとして部門スコープで取り込み | 部門（L2） |

この「データ最小化」方式なら、社内の私的なやり取りや人事関連メールが頭脳に流れ込むことを防ぎつつ、業務上必要な「顧客対応の全履歴」は組織資産にできる。
【要対応】メールの業務利用について就業規則・プライバシーポリシーへの明記と社内周知。

## 5. 導入前の権限棚卸し（必須タスク）

1. Notionの全チームスペース・トップページを一覧化し、§2のレベルを割り当てる
2. 現在の共有設定とあるべき設定の差分を洗い出し、修正する（特に「全員に公開されてしまっているL3/L4」を優先）
3. Driveの共有ドライブも同様に実施
4. 組織図（誰がどの部門・ロールか）をNotionの構造化データとして整備する — L2フィルタとボットの質問者判定の基礎データになる
5. 以後、四半期ごとに棚卸しを繰り返す（新規スペースの未分類チェック）

## 6. 監査

- ボット経由の全質問・回答・参照ページをログに記録する（改善用途と監査用途を兼ねる）
- L3以上の情報が回答に含まれた場合はアラートを管理者に通知（設計上発生しないはずの事象の検知）
- ログの閲覧権限は管理者＋役員に限定（NFR-2.4）
