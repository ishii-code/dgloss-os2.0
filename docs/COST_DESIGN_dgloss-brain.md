# ディグロス・ブレイン トークンコスト設計書（v0.1 ドラフト）

「全メールも含む全情報を対象にすると、トークン使用量がやばくならないか？」（2026-07-14 石井）への回答と設計。

---

## 1. 結論：都度「全情報を読む」わけではない

最重要の誤解ポイント：**「全情報にアクセスできる」＝「毎回全情報をAIに読ませる」ではない**。

質問が来たときの実際の流れ：

```
質問「シコメル様の契約条件は？」
  ↓ ① 検索（Drive検索/インデックス側が実行。LLMのトークンは消費しない）
  ↓ ② ヒットした候補の要約・抜粋だけをAIが見る（数千トークン）
  ↓ ③ 関連が強い上位2〜5ページだけ全文を読む（1〜3万トークン）
  ↓ ④ 回答を生成（数百〜2千トークン）
```

つまり1質問あたりのトークン消費は **社内情報の総量に関係なくほぼ一定**（目安2〜5万トークン）。メールが10万通あろうと100万通あろうと、1質問で読むのは関連する数件〜数十件だけ。「やばくなる」のは全文を毎回コンテキストに詰め込む設計にした場合だけで、本設計ではそうしない。

## 2. コストを最小化する6つの仕組み

### ① 検索→絞り込み→精読の段階型（アーキテクチャの基本）
上記の通り。検索インデックス（Google Drive検索／ベクトルDB）が候補を絞り、AIは絞られたものだけ読む。

### ② メール等の大量データはインデックス化（embedding は1回きり）
全メールのような大量コーパスは、取り込み時に一度だけベクトル化（embedding）する。
- embedding は専用の安価なモデル（Voyage AI等）で行い、費用は**文書1件につき1回きり**。全社メール数十万通（数億トークン規模）でも一括処理は数十〜百ドル程度、以後は新着分の差分だけ
- 質問時にコンテキストへ入るのは上位ヒットのチャンク（合計1〜2万トークン）のみ

### ③ プロンプトキャッシュ（読み取り 約1/10 の価格）
毎回同じ内容（システムプロンプト、ディグロス用語集、組織図要約）はキャッシュされ、**キャッシュ読み取りは通常入力の約0.1倍の料金**（書き込みは1.25倍だが1回だけ）。会話の履歴も同様にキャッシュされるため、追い質問のコストは大幅に下がる。設計上のルール：
- 共通コンテキスト（用語集等）はプロンプトの先頭に固定配置し、日付等の変動値を混ぜない
- ボット実装では `cache_control` を共通部の末尾に設定する

### ④ モデルの使い分け（役割別ルーティング）
| 役割 | モデル | 料金（入力/出力 per 100万トークン） |
|---|---|---|
| 検索結果の選別・抜粋、簡単なQ&A | Claude Haiku 4.5 | $1 / $5 |
| 回答合成（標準） | Claude Sonnet 5 | $3 / $15（2026-08末まで導入価格 $2 / $10） |
| 事業横断の分析・難問 | Claude Opus 4.8 | $5 / $25 |

大量に発生する「読む・選ぶ」作業を安いモデルに、最終回答だけ賢いモデルに任せる。

### ⑤ 夜間バッチの事前要約（プリコンピュート）＋ Batch API 50%オフ
リアルタイムに生データを読む代わりに、夜間バッチで「圧縮版」を作っておく：
- 顧客ごとの対応サマリー（メール・議事録から自動生成 → 顧客DBに転記）
- 週次の全社動向サマリー
- 議事録の決定事項抽出

これらの生成には **Batch API（全モデル50%オフ、24時間以内処理）** を使う。日中の質問はコンパクトなサマリーにヒットするため、精読するトークンがさらに減る。「聞かれる前に要約しておく」ことがコストと回答速度の両方に効く。

### ⑥ 上限とモニタリング
- ユーザー別・日別のトークン使用量をログから集計しダッシュボード化
- 1質問あたりの上限（例：入力10万トークン）を設定し、超える調査は「時間がかかります」と確認を挟む
- 月次予算アラート（例：予算の80%到達で管理者に通知）

## 3. 概算コスト（Phase 2、Sonnet 5標準・キャッシュあり）

| 項目 | 概算 |
|---|---|
| 1質問あたり | 入力2〜5万トークン（大半はキャッシュ読み＝0.1倍）＋出力1〜2千トークン ≒ **5〜15円/質問** |
| 全社50人が1日計100質問 | 月2万質問 ≒ **月2〜4万円** |
| メール初回インデックス化 | 一回きり 数千円〜1.5万円規模 |
| 夜間バッチ（要約生成、Batch API） | **月1〜3万円** |
| **合計目安** | **月5〜10万円**（利用が想定の3倍でも月30万円以内） |

※為替・利用パターンで変動する概算。Phase 1試用の実測値で必ず補正する。

## 4. アンチパターン（やってはいけない設計）

| アンチパターン | なぜダメか | 正解 |
|---|---|---|
| 全文書を毎回プロンプトに詰める | トークン消費が情報量に比例して爆発 | 検索→上位だけ精読（§2①） |
| メールを質問のたびにAPIで全件走査 | 遅い・高い・レート制限 | 事前インデックス化（§2②） |
| システムプロンプトに日付や乱数を入れる | キャッシュが毎回無効化され入力が全額課金 | 変動値は末尾に置く（§2③） |
| 全処理をOpusで実行 | 選別作業に5倍の料金を払うことになる | 役割別ルーティング（§2④） |
| 夜間バッチを通常APIで実行 | Batch APIなら同じ処理が半額 | Batch API（§2⑤） |
