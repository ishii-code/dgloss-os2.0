# ディグロス・ブレイン 要件定義書（v0.1 ドラフト）

設計書（`DESIGN_dgloss-brain.md`）を前提に、要件を整理したもの。
【要確認】の項目は経営判断が必要な未決事項。

---

## 1. 背景と目的

### 背景
- 会社の情報はNotion（イントラWiki・議事録・顧客DB・事業部ページ）とGoogle Workspace（Drive/Docs/スプレッドシート/Gmail）に分散して蓄積されている
- 「あの件どうなってた？」「○○様の契約条件は？」といった問いへの回答が、人への確認・ページ探しに依存しており、時間がかかる／人に依存する

### 目的
社内の誰もが、**自然言語で聞けば、社内情報に基づく出典付きの回答を数十秒以内に得られる** 状態を作る。

### 目的でないこと（スコープ外）
- 社外向け（顧客向け）チャットボット
- 基幹業務の自動化（受発注・請求処理等）※将来の発展形として排除はしない
- Notion・Google Workspaceの置き換え（既存ツールはそのまま使い続ける）

## 2. 利用者と利用シーン

### 利用者
| 区分 | 想定人数 | 主な用途 |
|---|---|---|
| 経営陣 | 数名 | 事業横断の状況把握、過去の意思決定の確認、週次サマリー |
| マネージャー | 〜10名 | 担当事業部の進捗・顧客状況・KPIの確認 |
| メンバー | 全社員 | 業務フロー・マニュアル・社内ルール・顧客情報の検索 |
| 新入社員 | 随時 | オンボーディング（会社ルール・用語・組織の質問） |

【要確認】Phase 2で全社員に開放するか、まず特定部門からか。

### 代表ユースケース
1. 「○○様との直近のMTGで決まったことは？」→ 議事録から決定事項を出典付きで回答
2. 「SP事業部のレベニューシェア契約の仕組みを教えて」→ 事業部ページ・契約資料から回答
3. 「経費精算のルールは？」→ イントラの人事・労務ページから回答
4. 「導入顧客のうち、直近1ヶ月で動きがあった案件は？」→ 顧客DB・議事録を横断して一覧化
5. 「先週の全社の動きをまとめて」→ 議事録・更新ページから週次サマリー生成（Phase 3.5）

## 3. 機能要件

### FR-1 質問応答（コア機能）
- FR-1.1 自然言語（日本語）の質問を受け付け、社内情報源を検索して回答を生成する
- FR-1.2 回答には**必ず出典（NotionページURL等）を付ける**。出典が見つからない場合は「見つからなかった」と明示し、推測で断定しない
- FR-1.3 出典ページの有効期限（Verification）が切れている場合、「情報が古い可能性がある」と警告を付す
- FR-1.4 会話の文脈を保持し、追い質問（「それの担当は誰？」）に対応する
- FR-1.5 ディグロス固有の用語・略称（SP＝セールスパートナー等）を理解する（文脈プロンプト／用語集で担保）

### FR-2 情報源（検索対象）
| 優先度 | 情報源 | 内容 | フェーズ |
|---|---|---|---|
| 必須 | Notion | イントラWiki、AI議事録、顧客DB、事業部ページ、業務フロー | Phase 1 |
| 必須 | Google Drive | 提案資料、契約関連、スプレッドシート | Phase 1 |
| 推奨 | Gmail／カレンダー | 個人の依頼・予定の確認（本人権限の範囲のみ） | Phase 1〜2 |
| 任意 | GitHub | 開発リポジトリ（開発メンバー向け） | Phase 2 |
| 検討 | Google Chatログ | 過去のやり取りの検索 | Phase 3（必要性が確認されたら） |
| 検討 | 基幹システム・通話ログ等 | AIテレアポ関連データ等 | Phase 3 |

【要確認】Google Chatログと通話ログを検索対象に含めるか（プライバシー配慮の社内合意が必要）。

### FR-3 インターフェース
- FR-3.1 【Phase 1】Claude（Web/モバイルアプリ）＋コネクタで利用できる
- FR-3.2 【Phase 2】Google Chatで `@頭脳` にメンション（DM・スペース両方）して質問できる
- FR-3.3 【Phase 2】回答に時間がかかる場合、先に受付応答を返し、完了後に回答を投稿する
- FR-3.4 【Phase 3.5】定期実行（週次経営サマリー等）を指定のChatスペースに自動投稿できる

### FR-4 運用・改善機能
- FR-4.1 「答えられなかった質問」を記録できる（Phase 1は手動ログ、Phase 2からボットが自動記録）
- FR-4.2 回答品質を評価する質問セット（ゴールデンセット）で、変更時に品質を検証できる
- FR-4.3 ユーザーが回答に👍/👎フィードバックを付けられる（Phase 2）

## 4. 非機能要件

### NFR-1 性能
- 通常の質問：**60秒以内**に回答（エージェント検索型の特性上、即答は要求しない）
- 受付応答（Chatボット）：3秒以内
- 同時利用：Phase 2時点で同時10ユーザー程度を想定

### NFR-2 セキュリティ・権限
- NFR-2.1 **質問者本人の権限で見える情報のみ**を検索・回答に使用する（元システムの権限に委任）
- NFR-2.2 頭脳用の「全権アカウント」を作らない。ボットのサービスアカウントに与える権限は最小限とし、付与範囲を文書化する
- NFR-2.3 機微情報（給与・評価・個人情報）はNotion/Drive側の権限設計で遮断する。【要確認】機微情報の扱いポリシー策定が前提
- NFR-2.4 質問・回答ログの保存方針を定める（改善に使う一方、私的な質問の閲覧範囲は限定する）【要確認】
- NFR-2.5 利用するLLM APIは学習に入力データを使用しない契約形態（Claude API標準）とする

### NFR-3 可用性・運用
- 業務時間内の利用を想定。24/365の厳格なSLAは設けない（ベストエフォート）
- 障害時は従来手段（Notion/Drive直接検索）で業務継続できるため、冗長化は行わない
- 管理者：1名以上（コネクタ・プロンプト・ボットの保守）【要確認】誰が担うか

### NFR-4 コスト
- Phase 1：Claude Team/Enterpriseのライセンス費のみ（利用人数分）
- Phase 2：Claude API従量課金＋Cloud Run実行費（小規模。目安：月数万円〜、利用量次第）
- Phase 3（RAG増設）：着手前に別途見積もり
- 【要確認】予算上限

### NFR-5 拡張性・ロックイン回避
- 頭脳層は薄く保ち、資産は「整備されたNotion」「文脈プロンプト」「評価セット」に置く（LLM乗り換え可能な構造）
- 情報源の追加はコネクタ／MCPの追加で対応できる構成とする

## 5. データ整備要件（システム外だが成否を左右する）

- DR-1 イントラDB全ページに**オーナー**を設定する
- DR-2 重要ページ（ポリシー・業務フロー・料金/契約条件）は**有効期限（Verification）を運用**する
- DR-3 会議の決定事項は議事録からイントラへ転記する運用を敷く（将来はAIが転記案を自動生成）
- DR-4 用語集（社内略称・商品名・顧客の呼称ゆれ）をNotionに1ページ作り、文脈プロンプトの元データとする

## 6. 制約・前提

- 既存ツール（Notion、Google Workspace）は継続利用する
- チャット基盤はGoogle Chat（Slack導入はしない）
- Google Chatボットには公式Claude連携がないため、Chat API＋Cloud Run＋Claude Agent SDKで自作する
- Phase 1はノーコード（コネクタ接続のみ）で開始できることを必須とする

## 7. 成功指標（KPI）

| 指標 | 目標（Phase 2終了時点の目安） |
|---|---|
| 週次アクティブ利用者 | 対象者の50%以上 |
| 回答成功率（評価セット） | 80%以上（出典付きで正答） |
| 「答えられなかった質問」の解消率 | 記録された質問の70%を翌月までにデータ整備で解消 |
| 情報探索時間の体感削減 | 利用者アンケートで「探す時間が減った」70%以上 |
