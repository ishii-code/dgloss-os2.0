# ディグロス・ブレイン 要件定義書（v0.2）

設計書（`DESIGN_dgloss-brain.md`）を前提に、要件を整理したもの。
権限の詳細は `ACCESS_CONTROL_dgloss-brain.md`、トークンコストの詳細は `COST_DESIGN_dgloss-brain.md` を参照。

**v0.2 更新（2026-07-14 石井決定）**：①全社展開＋情報レベル別の権限制御、②全メールを情報源に含める、③機微情報もアクセス制御の上で扱う。

## 1. 背景と目的

### 背景
- 会社の情報はGoogle Workspace（Drive/Docs/スプレッドシート/Gmail）に分散して蓄積されている（Notionは基本未使用。過去データのみ存在）
- 「あの件どうなってた？」「○○様の契約条件は？」といった問いへの回答が、人への確認・ページ探しに依存しており、時間がかかる／人に依存する

### 目的
社内の誰もが、**自然言語で聞けば、社内情報に基づく出典付きの回答を数十秒以内に得られる** 状態を作る。

### 目的でないこと（スコープ外）
- 社外向け（顧客向け）チャットボット
- 基幹業務の自動化（受発注・請求処理等）※将来の発展形として排除はしない
- Google Workspaceの置き換え（既存ツールはそのまま使い続ける。新ツールの導入もしない）

## 2. 利用者と利用シーン

### 利用者
| 区分 | 想定人数 | 主な用途 |
|---|---|---|
| 経営陣 | 数名 | 事業横断の状況把握、過去の意思決定の確認、週次サマリー |
| マネージャー | 〜10名 | 担当事業部の進捗・顧客状況・KPIの確認 |
| メンバー | 全社員 | 業務フロー・マニュアル・社内ルール・顧客情報の検索 |
| 新入社員 | 随時 | オンボーディング（会社ルール・用語・組織の質問） |

**決定：全社員に開放する。** ただし情報分類レベル（L1〜L4/P）に応じたアクセス制御を必須とする（`ACCESS_CONTROL_dgloss-brain.md` §2）。

### 代表ユースケース
1. 「○○様との直近のMTGで決まったことは？」→ 議事録から決定事項を出典付きで回答
2. 「SP事業部のレベニューシェア契約の仕組みを教えて」→ 事業部ページ・契約資料から回答
3. 「経費精算のルールは？」→ 会社Wiki（Google Docs）の人事・労務ページから回答
4. 「導入顧客のうち、直近1ヶ月で動きがあった案件は？」→ 顧客DB・議事録を横断して一覧化
5. 「先週の全社の動きをまとめて」→ 議事録・更新ページから週次サマリー生成（Phase 3.5）

## 3. 機能要件

### FR-1 質問応答（コア機能）
- FR-1.1 自然言語（日本語）の質問を受け付け、社内情報源を検索して回答を生成する
- FR-1.2 回答には**必ず出典（Drive文書・メール等へのリンク）を付ける**。出典が見つからない場合は「見つからなかった」と明示し、推測で断定しない
- FR-1.3 出典文書が文書台帳の見直し期限を過ぎている場合、「情報が古い可能性がある」と警告を付す
- FR-1.4 会話の文脈を保持し、追い質問（「それの担当は誰？」）に対応する
- FR-1.5 ディグロス固有の用語・略称（SP＝セールスパートナー等）を理解する（文脈プロンプト／用語集で担保）

### FR-2 情報源（検索対象）
| 優先度 | 情報源 | 内容 | フェーズ |
|---|---|---|---|
| 必須 | 会社Wiki（Google Docs） | 業務マニュアル、社内ルール、用語集、組織図（Phase 1で新規整備） | Phase 1 |
| 任意 | Notionレガシーデータ | 過去の議事録・顧客情報（移行 or 読み取り専用で参照） | Phase 2で判断 |
| 必須 | Google Drive | 提案資料、契約関連、スプレッドシート | Phase 1 |
| 必須 | Gmail（本人メール） | 本人のOAuth権限の範囲で本人のメールを検索 | Phase 1〜2 |
| **必須（決定）** | Gmail（全社メール） | 顧客ドメイン宛/発メールを抽出し顧客DBへ要約転記＋インデックス化。私的・人事メールは対象外（データ最小化） | Phase 2〜3 |
| 推奨 | カレンダー | 予定の確認（本人権限の範囲のみ） | Phase 1〜2 |
| 任意 | GitHub | 開発リポジトリ（開発メンバー向け） | Phase 2 |
| 検討 | Google Chatログ・通話ログ | 過去のやり取りの検索 | Phase 3（必要性が確認されたら） |

全社メールの取り込み方式とプライバシー配慮は `ACCESS_CONTROL_dgloss-brain.md` §4 に定義。就業規則・プライバシーポリシーへの明記と社内周知が導入の前提条件。

### FR-3 インターフェース
- FR-3.1 【Phase 1】Claude（Web/モバイルアプリ）＋コネクタで利用できる
- FR-3.2 【Phase 2】Google Chatで `@頭脳` にメンション（DM・スペース両方）して質問できる
- FR-3.3 【Phase 2】回答に時間がかかる場合、先に受付応答を返し、完了後に回答を投稿する
- FR-3.4 【Phase 3.5】定期実行（週次経営サマリー等）を指定のChatスペースに自動投稿できる

### FR-4 運用・改善機能
- FR-4.1 「答えられなかった質問」を記録できる（Phase 1は手動ログ、Phase 2からボットが自動記録）
- FR-4.2 回答品質を評価する質問セット（ゴールデンセット）で、変更時に品質を検証できる
- FR-4.3 ユーザーが回答に👍/👎フィードバックを付けられる（Phase 2）

## 4. 非機能要件

### NFR-1 性能
- 通常の質問：**60秒以内**に回答（エージェント検索型の特性上、即答は要求しない）
- 受付応答（Chatボット）：3秒以内
- 同時利用：Phase 2時点で同時10ユーザー程度を想定

### NFR-2 セキュリティ・権限
- NFR-2.1 **質問者本人の権限で見える情報のみ**を検索・回答に使用する（元システムの権限に委任）
- NFR-2.2 頭脳用の「全権アカウント」を作らない。ボットのサービスアカウントに与える権限は最小限とし、付与範囲を文書化する
- NFR-2.3 **（決定）機微情報（給与・評価・個人情報）はL4に分類し、アクセス制御の上で扱う。** 情報分類（L1〜L4/P）とロール別アクセス権は `ACCESS_CONTROL_dgloss-brain.md` §2 のマトリクスに従う。導入前に権限棚卸し（同 §5）を必須実施
- NFR-2.4 質問・回答・参照ページの全ログを記録する。ログの閲覧は管理者＋役員に限定。L3以上の情報が回答に含まれた場合は管理者にアラート
- NFR-2.5 利用するLLM APIは学習に入力データを使用しない契約形態（Claude API標準）とする

### NFR-3 可用性・運用
- 業務時間内の利用を想定。24/365の厳格なSLAは設けない（ベストエフォート）
- 障害時は従来手段（Drive直接検索）で業務継続できるため、冗長化は行わない
- 管理者：1名以上（コネクタ・プロンプト・ボットの保守）【要確認】誰が担うか

### NFR-4 コスト
- Phase 1：Claude Team/Enterpriseのライセンス費のみ（利用人数分）
- Phase 2：Claude API従量課金＋Cloud Run実行費。概算 **月5〜10万円**（内訳と最適化設計は `COST_DESIGN_dgloss-brain.md`）
- コスト最適化を設計要件とする：段階型検索、プロンプトキャッシュ、モデル別ルーティング（Haiku/Sonnet/Opus）、夜間バッチのBatch API利用、メールの事前インデックス化
- ユーザー別・月次のトークン使用量モニタリングと予算アラートを実装する
- 【要確認】予算上限

### NFR-5 拡張性・ロックイン回避
- 頭脳層は薄く保ち、資産は「整備されたGoogle Workspace（会社Wiki・共有ドライブ）」「文脈プロンプト」「評価セット」に置く（LLM乗り換え可能な構造）
- 情報源の追加はコネクタ／MCPの追加で対応できる構成とする

## 5. データ整備要件（システム外だが成否を左右する）

- DR-1 情報分類レベル（L1〜L4）に対応した**共有ドライブ構成**を設計し、会社の資料を個人マイドライブから移す
- DR-2 **会社Wiki（Google Docs）を新規整備**する — 業務マニュアル・社内ルール・用語集・組織図。まずL1の頻出質問トップ20をカバーする分から
- DR-3 重要文書の**台帳スプレッドシート**（文書名・オーナー・最終見直し日）を運用する
- DR-4 会議の決定事項は議事録から会社Wikiへ転記する運用を敷く（将来はAIが転記案を自動生成）
- DR-5 用語集（社内略称・商品名・顧客の呼称ゆれ）をDocsに1枚作り、文脈プロンプトの元データとする
- DR-6 Notionレガシーデータの棚卸し：残す価値のあるもの（議事録・顧客情報）を特定し、移行 or 参照方針を決める

## 6. 制約・前提

- 既存ツール（Google Workspace）は継続利用する。Notion等の新規ツール導入は行わない
- チャット基盤はGoogle Chat（Slack導入はしない）
- Google Chatボットには公式Claude連携がないため、Chat API＋Cloud Run＋Claude Agent SDKで自作する
- Phase 1はノーコード（コネクタ接続のみ）で開始できることを必須とする

## 7. 成功指標（KPI）

| 指標 | 目標（Phase 2終了時点の目安） |
|---|---|
| 週次アクティブ利用者 | 対象者の50%以上 |
| 回答成功率（評価セット） | 80%以上（出典付きで正答） |
| 「答えられなかった質問」の解消率 | 記録された質問の70%を翌月までにデータ整備で解消 |
| 情報探索時間の体感削減 | 利用者アンケートで「探す時間が減った」70%以上 |
