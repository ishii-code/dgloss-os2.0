# ディグロス・ブレイン セキュリティ設計・脅威モデル（v0.1）

「全データにアクセスできる頭脳がハッキング・流出したら会社が終わる」という懸念（2026-07-14 石井）への回答。
`ACCESS_CONTROL_dgloss-brain.md`（権限＝誰が何を見られるか）と対で、本書は**攻撃・漏洩の観点**を扱う。

---

## 0. 結論（先に）

1. **この設計は「全データを1箇所に複製」しない。** 盗める中央コピーが存在しないこと自体が最大の防御（§1）。
2. **「絶対安全」は存在しない。** 守るべき急所（§3）を固めるかで安全性が決まる。現状スケルトンは急所未実装。
3. **最悪被害（blast radius）を設計で限定する。** 1箇所破られても全社全滅にならない構造を作る（§4）。
4. セキュリティに関わる変更は**石井の承認を得てから**進める（グローバル規約）。

---

## 1. 基本原則：集めない・複製しない・マスターキーを作らない

| 危険な作り（不採用） | 本設計（採用） | 効果 |
|---|---|---|
| 全社データを中央DB/ベクトルDBに複製 | データはGoogle Workspaceに置いたままライブ検索（`DESIGN`方針A①） | **盗める中央コピーが無い** |
| ボットが全データを読める共有アカウント（ドメインワイド委任） | 検索は毎回「質問者本人のOAuth」で実行（`ACCESS_CONTROL`§3） | **マスターキーが無い** |
| AIに外部送信ツールを持たせる | ツールは検索（drive/gmail）のみ。外部へデータを送る口を持たせない | **持ち出し経路が無い** |

この3つが崩れると安全性は根本から崩れる。以降の実装・レビューで**この3原則の違反を最優先で検出**する。

## 2. 資産・信頼境界

**守る資産**
- A1: OAuthトークン保管庫（各ユーザーの検索用の鍵）← **最重要**
- A2: Google Workspace上の社内データ本体
- A3: Anthropic APIキー
- A4: QA/監査ログ（質問・回答に機密が写り込む）
- A5: Chatアプリのサービスアカウント

**信頼境界**
```
[ユーザー/Google Chat] --JWT--> [Cloud Run ボット] --APIキー--> [Anthropic]
                                      │
                                      ├--ユーザーOAuthトークン--> [Google Drive/Gmail API]
                                      └--> [トークン保管庫 / ログ保管庫]
```

## 4. 最悪被害の限定（Blast Radius）

「1箇所破られたら全社終わり」を避けるための、被害範囲の設計上の上限：

- **中央データコピー無し**（§1）→ サーバ侵害でも"全社データの束"は盗めない
- **トークンは本人スコープ・読み取り専用**→ 1トークン漏洩の被害は「その1人が見られる範囲の読み取り」に限定（書き換え・削除は不可）
- **一括失効ボタン**（T1対策）→ 侵害検知時に全トークンを失効し被害を即座に止める
- **共有ドライブのL1〜L4分離**（`ACCESS_CONTROL`§2）→ そもそも1アカウントが会社の全機微に触れられない権限構造にしておく（頭脳以前の土台）

→ 目標：**「どのコンポーネントが1つ破られても、被害は"特定ユーザーが見られる範囲の読み取り"に収まる」** 状態。

## 5. インシデント対応（最低限の備え）

- **失効**：全ユーザーOAuthトークンの一括失効手順（Google側revoke＋保管庫クリア）
- **鍵ローテーション**：APIキー・KMS鍵・OAuthクライアント秘密の交換手順
- **監査**：全質問・回答・参照ページのログ（`ACCESS_CONTROL`§6）で「何が参照されたか」を事後追跡可能に
- **アラート**：L3以上の情報が回答に含まれた場合／異常なトークン使用量／失効イベントを管理者通知

### 7.1 ログの質問本文（判断2の選択肢・分かりやすい説明）

ログには「誰が・いつ・何を聞いて・答えられたか」を残す。目的は**システムを賢くするため**（よく聞かれる質問→Wiki整備、答えられなかった質問→データ補充）。
ただし質問文そのものに機密（顧客名・給与の話など）が写り込むため、質問"本文"をどこまで残すかを決める。

| 案 | ログに残る質問本文の例 | 改善のしやすさ | 安全性 |
|---|---|---|---|
| A 平文保存 | `シコメル様の契約条件は？` をそのまま保存 | ◎（何を聞かれたか完全に分かる） | △（ログ保管庫自体が機密。閲覧を役員＋管理者に限定necessary） |
| B 機密度マスク | 通常はそのまま／機微語（給与・評価・個人名等）や L3以上を触った質問は `[マスク]契約条件は？` 等に伏せる | ○ | ○（バランス型） |
| C メタのみ | 本文は残さず「誰が・いつ・答えられたか・件数」だけ | ×（何を聞かれたか分からず改善が鈍る） | ◎ |

**推奨：B（機密度マスク）。** 改善に必要な情報を残しつつ、機微な質問だけ伏せる。いずれの案でもログ保管庫の閲覧権限は管理者＋役員に限定する（T5）。
